# iPad and Mac condition check

[Magyar](README.md) | **English**

A tool for buying used iPads, iPhones and Macs. An iPad/iPhone seller first runs the USB reader, then performs browser tests on the device being sold. Results and test steps are saved to the buyer's private Sheet; at the end, a single combined report is assembled and, if requested at the beginning, emailed once to the seller.

The code is public so that the seller (and anyone else) can see exactly what the page reads and what it sends.

**Example report:** [docs/example-report.md](docs/example-report.md). It uses invented data and is generated by the same code as the real report (in Hungarian, like the real one), and a test makes sure it always matches.

## For sellers: what does the page read?

| What we read                                                                         | What we never read                                                      |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| battery cycle count, maximum capacity, and optional stress-test samples              | passwords, Apple ID, email addresses stored on the device, phone number |
| device type, USB hardware platform, storage size, system version                     | photos, messages, contacts, files                                       |
| whether you are signed out of your Apple ID (you tell us)                            | app and Safari tab contents, browsing history                           |
| on a Mac: Activation Lock state, managed by an organization yes/no                   | IMEI, device name, location, Wi-Fi networks, MAC addresses, UDID        |
| complete serial with USB data; sharing remains optional in the Mac web report        |                                                                         |
| voluntarily entered email address, only for one-time delivery of the combined report | automatic reading of email addresses from the device                    |
| temporary app/tab metadata for Safari opening: title and URL, excluded from reports  | Safari tab contents and cookies                                         |

The USB reader asks for the invitation code and consent to save test data to the buyer's private Sheet before reading. Once reading finishes, the backend saves the USB data to the Sheet without sending any email to the buyer. There is no clipboard copying or data pasting. After saving USB data, the reader offers an optional battery stress test (during 1080p 60fps video playback, with configurable duration in minutes and sampling interval in seconds, default 5 min / 1 s): samples are synced in batches to the `Akku mérés` sheet tab, and the summary is added to the USB section in `Tesztlépések` and the final report. On the device being sold, after consent, browser test steps and partial results are saved to the Sheet as they happen; the combined report is finalized and displayed after preview approval and **Finish test** (**Teszt befejezése**).

An optional seller email report can be requested once at the start: in the reader before reading on iPad/iPhone, or when starting the browser test on a Mac. The address is kept only in memory until delivery (in the running reader or the Mac browser tab); it is never written to the Sheet, ScriptProperties, CacheService, application logs, or browser storage, and is excluded from reports and URLs. At the end, a single combined (or incomplete, if interrupted) report is sent to the seller. The email provider necessarily processes recipient addresses for delivery and its own mail records.

### How can you check this?

- [web/parse.js](web/parse.js): the readers. They only read a fixed list of fields and ignore everything else. The serial number fingerprint and the report structure are built here too.
- [web/seller.js](web/seller.js): the wizard. Network requests only go through the `send()` function after seller consent. The file is built from the parts in [src/web/seller/](src/web/seller/) (a plain concatenation that does not change how it works), both are in the repository, and a test guards that they always match.
- [web/index.html](web/index.html): the page loads no third-party scripts, only its own files.
- [backend/Code.gs](backend/Code.gs): the receiving Google Apps Script. It accepts nothing without an invitation, stores invite state in `Meghívók`, test steps/report sections in `Tesztlépések`, and battery stress-test time-series samples in `Akku mérés`, and sends a single combined email to the seller at the end if requested.

The deployed Apps Script cannot be verified from the outside, only the file in this repository can.

### How the serial number is handled

The USB read includes the complete serial, for which the reader requests consent before reading. At the end of the test, the backend merges the saved USB data and the browser test results into a single combined report. The Mac browser flow still offers serial sharing or a fingerprint.

## How does it work?

There are two modes:

1. **Seller flow** ([web/](web/), [tool/ipad_audit/reader.py](tool/ipad_audit/reader.py), [tool/ipad_audit/battery_test.py](tool/ipad_audit/battery_test.py), [tool/ipad_audit/audit.py](tool/ipad_audit/audit.py)): the website explains the process. The USB reader runs on the computer, saves the USB data to the Sheet after consent and an optional seller email address, offers the optional battery stress test (during 1080p 60fps video playback, sampling to the `Akku mérés` sheet tab), tries to open the audit page in Safari on the iPad/iPhone (or prints the `#CODE.SESSION` continuation link), and stays open to follow the web test steps. At the end of the web tests, the combined report is saved in the Sheet and, if requested at the beginning, the reader triggers the one-time combined email. The Mac flow still uses a read-only Terminal command.
2. **Receiving program** ([tool/](tool/), [web/receiver/](web/receiver/)): runs on the buyer's computer and reads the iPad over USB (`pymobiledevice3`). This is a check on the buyer's own computer, but it is not cryptographic proof of the origin of the data or parts.

Missing USB fields and unsupported browser tests are marked unknown/not tested, not as hardware faults. Data from a seller-controlled computer is not cryptographic proof.

Data path: USB reader and the device browser -> Google Apps Script (`Meghívók` and `Tesztlépések` sheets); at the end, a combined report and—if requested at the beginning—a single seller email. An uncertain email delivery is not automatically repeated.

The daily mail allowance is 20 emails (`DAILY_MAILS`).

The Safari-opening attempt requires Web Inspector, not Remote Automation. The program does not enable this setting. The library temporarily receives metadata for inspectable apps and tabs; we do not store or transmit it, and do not request page contents, cookies, or history. Navigation only targets the audit page or a blank Safari tab. The attempt has a timeout; actual iOS 9 device behavior still needs verification. Lack of Web Inspector does not prevent using the continuation link printed by the reader.

## Status

- In the receiving program's battery report, the `OriginalBattery` system log value does not verify battery authenticity, whether it was replaced, or whether the service was authorized. If the value is missing, the origin is unknown. The battery manufacturer and service history are not currently verified.
- The iPad file reader in the wizard relies on assumed field names (`Last_Value_CycleCount`, `MaximumCapacityPercent`) and still needs to be checked against a real file.
- The `system_profiler` key names used by the Mac command still need to be checked on a real Mac.
- The in-browser hardware test (touch, motion, audio, camera, display) is part of the wizard. Touch, camera and microphone still need checking on a real device. A test for the buttons and the headphone jack does not exist yet.
- The seller USB report and web test report can be sent separately using the same invitation. The previous flow gallery documents the older, single-report process; the new flow has a separate integration test.
- The wizard targets Safari 9.1 (iOS 9.3.5) and newer, so it uses ES5 only, without `fetch` or `TextEncoder`. The iOS 9.3.5 menu names were checked on a real iPad, the names for other versions come from Apple's Hungarian pages and guides and still need checking on real devices.

## Development

Edit the wizard code in the part files of [src/web/seller/](src/web/seller/), then run the concatenation (web/seller.js is built from them, and a test fails if you forget):

```
npm run build:web
```

All unit tests (the readers, the backend, the documentation, and a guard that forbids modern syntax in the web/ folder because of the iOS 9 Safari) run with one command:

```
npm test
```

GitLab and GitHub both run it after every push, and GitLab Pages only updates after a green test.

Tests for the in-browser readers:

```
node --test tests/seller_parse.test.js
```

The following commands are for Linux. The Python programs require the project's `.venv` environment and the dependencies in [requirements.txt](requirements.txt).

Start the web page:

```bash
npm start
```

Start the USB reader: after the invitation code, consent, and optional seller email address, it reads the device, asks the backend to save the USB data in the Sheet, and tries to navigate the device's Safari to the audit page. Continue web tests on the device being sold. If Safari opening fails, the program prints a prominent heading, separator lines, and the `#CODE.SESSION` continuation URL on its own line, then stays open to follow the web test steps and trigger the combined seller email at the end if requested. The reader does not open a computer browser or start a local web server.

```bash
npm run usb
```

The end-to-end integration test uses a mock backend and sends no real email. It requires the project Python environment and Google Chrome:

```bash
npm run test:integration
```

Start the receiving program (it asks for a real invite code, connects to the backend, and sends the report at the end):

```bash
npm run audit
```

The web page can also be started directly with the script:

```
scripts/serve.sh
```

The page then opens at `http://localhost:8766/`. The port is always 8766, and the script also prints the address to use from an iPad. Typing `DEMO` into the invite code field starts a trial mode: the Send button sends nothing and shows what would have been sent. The seller opens the plain address and types the 9-digit invite code on the first screen. A `#CODE` appended to the address only prefills the field. The `#DEMO` page shows a list at the top with a button for every screen and state (iPad iOS 9 to 17, a computer with USB, Mac, every preview and final screen) that jumps straight there. Deep links work too, for example `#DEMO-ios9-review-log`. They exist only on the `#DEMO` address and have no effect with a real invite code.

The whole flow with Mermaid diagrams and the walked-through scenarios: [docs/flows.en.md](docs/flows.en.md). The scenarios are Playwright tests; after `npm install`, `npm run flows` runs them and builds a step-by-step screenshot gallery in `flows-out/index.html`.

Dependencies of the Python part: [requirements.txt](requirements.txt). Tests: [tests/test_core.py](tests/test_core.py).

## Setup

1. Create a Google Sheet, open Extensions > Apps Script, and paste the contents of [backend/Code.gs](backend/Code.gs) and [backend/appsscript.json](backend/appsscript.json).
2. Deploy it as a web app (execute as: you, access: anyone). Put the resulting `/exec` address into [web/config.js](web/config.js) and [tool/ipad_audit/config.py](tool/ipad_audit/config.py).
3. The "New invite" item of the sheet's "iPad audit" menu issues a code valid for 72 hours that allows one USB report and one web test report, and a ready message with the full link (the code is in it, so the seller does not have to type anything). The link also goes into the "Link" column of the sheet. The link is built from SITE_URL at the top of [backend/Code.gs](backend/Code.gs), change it to your own address.
4. [.gitlab-ci.yml](.gitlab-ci.yml) publishes the `web/` folder to GitLab Pages.

After backend changes, publish a new deployment version in Apps Script. Editing the local file or saving it in the editor does not update the running web app. Use Deploy > Manage deployments > Edit > New version to update the existing deployment, preserving its endpoint address and allowing a rollback to the previous version. The two-report flow requires the new report action; the previous deployment returns an unknown action error.

After saving, select and run the email-free check from the editor's function list:

```text
checkDeployment
```

The check reports whether the invitation sheet and recipient are available, and the remaining MailApp quota. It does not create an invitation or send an email. Verify actual delivery in the recipient's mailbox with a separate test invitation and fictional data.

The `/exec` address is not a secret. Protection comes from the invite code and the daily mail limit.
